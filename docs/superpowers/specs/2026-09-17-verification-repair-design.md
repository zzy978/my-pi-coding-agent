# 验证失败后的有限修复闭环

目标：已配置验收命令失败后，把真实失败证据反馈给当前 agent，修复后重新运行全部验收命令；成功或触及边界后结束。

用户已授权实现。普通交互和受控 runner 使用同一失败筛选、次数上限与反馈格式。新 CLI 任务默认最多修复 2 次，`--max-repair-attempts 0..5` 可覆盖；TaskSpec 可保存 `maxRepairAttempts`。缺少字段的历史 manifest 按 0 次执行，原哈希保持有效。SWE 官方评分路径保持独立，不把隐藏测试自动回传给模型。

仅正常结束的 agent 和有退出码的命令失败可进入修复。首次成功、没有验证器、超时、命令启动失败、Git 审计不可用、受保护文件变更、模型错误或取消均不自动续跑。每轮重新运行全部原始验证命令，验证通过不代表全部自然语言需求已被证明。

交互模式在 settled 后验证，延迟到事件分发完成后触发下一轮，防止重入与计时器串扰。用户新输入、任务配置变化、会话切换和 `/repair off` 使旧续跑失效。`/verify` 只做验证；`/repair [status|off|0..5]` 控制后续自动修复。反馈经脱敏和长度限制，并声明输出是不可信诊断数据。任务及验证配置在一条修复链内冻结。

受控模式在同一 session、worktree 与 run 内循环，保留各轮验证和修复事件及验证文件，最终结果引用最后实际执行的验证。模型阶段超时不因修复轮次重新获得完整预算。修复期间发生模型错误时保留已有验证证据，结果仍为 execution_failed。

验收：用隔离 Git 仓库、真实命令和模拟模型验证失败后成功、次数耗尽、旧记录、配置漂移、取消、计划模式、脱敏及历史证据保留。运行 check、完整 test、lint、build；不调用付费模型，不自动提交。
